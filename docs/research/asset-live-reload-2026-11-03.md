# Asset live-reload investigation — 2026-11-03

## Scope and evidence limits

Two rare reports: replaced assets revert after seconds, or many assets revert together after minutes. Reported affected types include meshes, textures/images and audio. Neither affected client is currently reproducible. All tests below distinguish a **new fetch receiving original bytes** from an **already-loaded renderer/audio resource being actively invalidated**. No in-game causal trace of either rare event exists yet.

## Common client asset-fetch path

Symbolized, unmodified Roblox Studio **macOS 0.735.19.7351131** (`TOER-AI-TRAINING/reference/roblox-macos-studio-0.735.19.7351131/RobloxStudio`):

- `RBX::AssetRequest::sendAssetDeliveryV1` at `0x100049528` calls `RBX::HttpCache::HttpRedirectCache::get2` at `0x1000497d6` and, when a usable redirect is available, `RBX::AssetRequest::sendCdnRequest` at `0x100049985`. This route does **not require another `/v1/assets/batch` request**.
- The newer AssetProvider implementation has `AssetResolutionRedirectCacheState::next` (`0x1034bcee2`), `AssetResolutionCDNState::next` (`0x1034be64c`), `AssetResolutionReAuthenticateAssetState::next` (`0x1034bdaf8`), and `AssetDeliveryRefreshWorkflow` (`0x1034b91b8`). `AssetResolutionRedirectCacheState::next` checks `CDN::needsReauthentication` (`0x1034bd2c0`); signed URL refresh is a request-resolution path, not demonstrated to be an autonomous renderer reload.
- The **current unmodified 0.743.0.7431133** binary retains RTTI/string names `AssetResolutionRedirectCacheState`, `AssetResolutionReAuthenticateAssetState`, and `AssetDeliveryRefreshWorkflow`. The precise 0.735 instruction offsets/branches are **not** a same-build proof for 0.743.
- `ContentProvider::invalidateCache` (`0x1000902ee`) updates fetch status, invalidates an HTTP cache file, and emits a content-ID signal. Its observed direct calls in 0.735 are Studio file synchronization, Studio image-manager force reload and FBX import retry; this is **not** proof of a periodic gameplay-wide cache purge. `ContentProvider::invalidateBadUrl` (`0x100090984`) removes `AsyncHttpQueue` bad-URL state, with permission/failure and Studio caller paths.
- The `FStringHttpCacheAssetIdRefetchList` flag is read by `HttpCacheAssetDeliveryBlocklist::fetchBlockList` (`0x102f5a2b2`), whose URL check calls `getAssetIdFromUrl`. It affects eligibility for **HTTP cache** hits, not a proven way to invalidate a rendered asset on demand. `FFlagHttpCacheForcedAssetEviction` likewise did not produce a spontaneous cross-type visible reload during the prior native Studio test.

## Fleasion reproducible mechanisms

Current `feat/rewrite-ui-v2`, HEAD `9dc7b4a` at investigation:

1. `TextureStripper.process_batch_response` stores pending local/CDN replacement routes under the **original CDN host + URL path** (`src/fleasion/proxy/addons/texture_stripper.py`). `check_cdn_request` consumes `_local_redirects` and `_cdn_redirects` with `.pop()`. The first matching GET is replaced; subsequent GETs for the same CDN path are upstream originals unless a new batch re-registers that route. `src/fleasion/proxy/server.py` only intercepts CDN GET in the short-circuit path. HEAD no longer consumes the route (fixed in `9dc7b4a`).
2. A fake-upstream, real HTTPS explicit-proxy replay reproduced `batch → first CDN GET = replacement → second same CDN GET = Roblox original` for **image**, **audio**, and **mesh**. All three passed the negative-behavior assertions in `/tmp/fleasion_multitype_{image,audio,mesh}_refresh_20261103.py`. This proves a Fleasion fallback, **not** that a real affected client made the second request or swapped an in-use resource.
3. A separate synthetic two-ID batch showed that a replaced asset ID `111` and unrelated ID `222` sharing **one identical content-hash CDN path** result in one route. The first request (regardless of which ID caused it) gets the replacement, the second gets upstream. This makes blindly retaining original-path routes **unsafe**: it would apply one asset's replacement to all distinct assets with that content hash.
4. Local replacement responses currently lack `Cache-Control`, `ETag` and `Last-Modified`, while an actual CDN HEAD/GET sample contained a long `max-age`, ETag and Last-Modified. This can affect revalidation and refetch patterns but is **not** evidence that Roblox automatically refreshes already-loaded content.
5. At investigation baseline, `_serve_local_file` returned full `200 OK` for `Range: bytes=0-5` without `Content-Range` (`/tmp/fleasion_multitype_audio_range_refresh_20261103.py`). A subsequent targeted fix now returns `206 Partial Content` with valid byte ranges and `416` for unsatisfiable ranges; verified by real HTTPS proxy replay (`/tmp/fleasion_multitype_audio_range_afterfix_20261103.py`). This protocol fix does **not** solve the consumed one-shot route or the spontaneous live-reload trigger.
6. The older Windows log `/tmp/fleasion-asset-reload-20261103.log` recorded near-simultaneous TLS splice connection resets against assetdelivery/CDN/gamejoin/clientsettings at `21:49:50`, followed by a user's reported later cascade. Connection resets could cause renewed loads, but there is **no** request/response-to-visual-reversion proof.

## Proposed engineering direction

- Prototype **per-asset synthetic CDN locations** returned to the client in the intercepted batch response for local/CDN replacements. Each location must identify the **original asset ID and TexturePack slot**, not only the original content-hash URL, so both repeated GETs and shared-content IDs can be routed independently. Keep the mapping until configuration-generation invalidation; bound lifecycle/retention safely. Do not blindly persist the original CDN path.
- Validate the synthetic location in a real client before enabling by default: CDN host/path format, authentication checks, redirected response caching, repeated GETs across connections, concurrent same-content different-ID assets, non-proxied reconnects, texture packs, SolidModel response-dependent injections, and rig-detect animations all require testing.
- Complete consistent `HEAD`/conditional response handling and coherent caching headers for replacement bodies; the targeted `GET` single-byte-range fix is implemented. Preserve retry semantics and avoid serving incorrect original metadata for a synthetic replacement URL. Avoid comparing or recording signed query tokens; use host+hash of normalized path only in diagnostic logs.
- To **force an already-loaded asset to update live**, prove a specific client-side invalidation/rebind mechanism first. A fresh CDN fetch is necessary in some paths but not sufficient to make a renderer or audio object discard existing content. Nothing observed so far proves a network-only universal hot-reload trigger.

## 2026-11-03 follow-up: V2 delivery and HTTP/3 experiments

Reports of spontaneous asset reversion predate and postdate the October 2026 networking changes. Do **not** attribute either rare symptom to V2, compression, or QUIC without a same-client event trace.

Public, read-only calls to `https://assetdelivery.roblox.com/v1/assets/batch` and `/v2/assets/batch` used the same public image ID and request body. **Both returned HTTP/2 200, ordinary JSON and no Content-Encoding header**. The V1 response contained a singular `location`; V2 contained `locations: [{"assetFormat": "source", "location": "https://fts.rbxcdn.com/<hash>?<signed-query>"}]`. A public TexturePack sample used the same V2 shape. The CDN URLs in both schemas still targeted `fts.rbxcdn.com`; signed parameters were not persisted into this report.

The downloadable October 9 FastFlag diffs (`~/Downloads/fflags_6e9ac4c8a005.diff` and `fflags_e4e0e63c3f71.diff`) document staged `DFFlagRbxTransportQuicEmptyPayloadNoFinFix3` and `DFFlagRbxTransportQuicStableStreamContexts`. `~/Downloads/CppTree(1).txt` and the original Studio 0.743 Mach-O contain `RbxTransport::Http::H3ClientConnection`/`nghttp3` and `AssetProvider::BatchAssetApiV2*` types, while the current Studio Mach-O **also retains the literal `/v1/assets/batch`**. The evidence supports coexisting HTTP versions and CDN H3 experiments, not the claim that every asset fetch migrated into gameplay QUIC transport.

The publicly readable `ZPublicGatewayCompression` PCDesktopClient flag bucket currently exposes `DFFlagHttp3FtsReqs3=True`, `DFFlagTestHttp3Reqs2=True`, `DFFlagTestHttp3Reqs3=True`, `FFlagEnableZstdForClientSettings=True`, `FFlagEnableZstdDictionaryForClientSettings=True`, and `FStringPublicGatewayCompressTestChannel=enabled`. Such flags **do not establish what transport any individual player session selected**. Shared-dictionary `dcz` is explicitly handled by Fleasion only for ClientSettings response transformation; other unsupported compressed request encodings are now forwarded byte-identically rather than decoded incorrectly or having Content-Encoding stripped. The ordinary public V1/V2 batch samples did **not** demonstrate compressed batches.

This follow-up adds exact V1/V2 endpoint recognition, nested V2 locations for the replacer and cache scraper, V1/V2 direct ID routes, safe raw passthrough for unmodified or unknown compressed batches, and tests for HTTPS and HTTP/2. Distinct asset IDs sharing a CDN hash are now tracked independently in the scraper; the **replacer remains one-shot** and still needs per-asset synthetic URLs and real-client validation. HTTP/3 over QUIC is **outside** the existing HTTP/1–2 plaintext proxy handlers and was not added as a new transport. For a V2 response with multiple distinct asset formats, each location may require format-specific replacement payload handling; the current router associates all returned CDN locations with one rule, which remains a compatibility risk to investigate before treating multi-format V2 support as complete.

The public direct-ID endpoint responses also differ: `GET /v1/asset/?id=<public-image-id>` returns `302` with a CDN `Location`, while `GET /v2/asset/?id=...` and `GET /v2/assetId/...` return a JSON object with `locations`, and `GET /v1/assetId/...` returns a JSON object with singular `location`. The direct-ID rewrite changes only the requested asset ID and preserves the original endpoint's response format for the client; it must not assume every direct request expects a redirect. HEAD returned 404 in this one public probe and was not used to infer GET behavior.

Test suite after updating the pre-existing fixtures to model current semantics: **1,959 passed, 17 skipped, 27 subtests passed, 4 Qt deprecation warnings**, full `pytest -q --maxfail=1` run on Fedora 2026-11-03. The stale fixtures were (1) a mock replacer missing the exact direct-ID rewrite method, and (2) a CDN local replacement check using POST, although the actual proxy explicitly short-circuits only GET requests. Neither change modifies production forwarding behavior.

Remaining known limitation: local-file/CDN-URL replacements still require observing a batch response; the direct V1/V2 ID path rewrite currently supports public **ID-to-ID** targets only. Compressed V2 response bodies that use an unavailable dictionary will pass through intact but cannot have replacement URLs registered. The existing HTTP/1–2 interceptors cannot inspect independent HTTP/3 QUIC connections. Repository-wide Pyright currently reports 246 diagnostics confined to unrelated unchanged test files; explicit type-check of every changed source and test file reports zero errors.

## Opt-in synthetic CDN route prototype (local commit, pending native validation)

The replacement router now supports `FLEASION_ASSET_SYNTHETIC_CDN=1`, read at startup. This is **disabled by default** until a real Roblox client proves it accepts synthetic CDN locations. In this mode, each single-location V1 or V2 batch response entry whose replacement is a local file or CDN URL receives its own opaque `https://fts.rbxcdn.com/__fleasion__/asset/<random-hex>` location (or the equivalent `contentdelivery.roblox.com` host). The random token is not derived from the asset ID or authentication/signature query. It prevents two asset IDs sharing an original content hash from sharing one replacement route. Existing cache-scraper hooks continue receiving the original upstream batch metadata before the proxy forwards the rewritten response.

The proxy stores the mapping under a shared lock, handles repeated GETs without consuming it, supports HEAD for managed local paths and range GETs, and returns `410 Gone` for stale/evicted synthetic paths instead of forwarding a generated URL to Roblox. Other unsupported methods are answered locally with `405`. The route table is bounded at 8,192 entries, least-recently-used, and cleared on proxy stop, cache clear, or replacement configuration-generation change. An evicted URL may return `410`, so the cap and lifecycle need real-game telemetry before default rollout. No original signed CDN query is copied into synthetic locations.

The feature does **not** synthesize a URL when a V2 response lists multiple different `assetFormat` entries, a URL is outside the approved CDN HTTPS origins, or an animation needs the upstream body for rig matching. SolidModel response-dependent transformations likewise use the old route. These cases preserve prior behavior and are not claimed fully persistent. CDN/Local rules for *direct* ID endpoints remain separate from V1/V2 batch replacement; ID-to-ID direct rewriting already exists. HTTP/3/QUIC continues to be outside the HTTP/1–2 decrypted interceptors; this prototype does not force fallback to HTTP/2 and must not be enabled by default on untested clients.

The loopback HTTPS tests use a synthetic upstream that returns a shared CDN content hash for two different logical asset IDs, and verify distinct URLs, three successive correct asset responses, range/HEAD, configuration reset, stale-response `410`, URL eligibility checks and route-budget eviction. An independent HTTP/2 test verifies repeat GET, HEAD, and stale `410` on the same multiplexed connection with zero upstream CDN requests. No active Roblox client was used, so engine-side URL validation/caching and live visual resource reload remain unproven.

Verification on Fedora: `389 passed, 3 subtests passed` for the complete `test_proxy_*`, `test_tls_*`, texture stripper, asset-delivery, synthetic CDN, and decrypted HTTP/2 transport groups. Changed-file Ruff and strict Pyright checks both passed. Two attempted repository-wide runs stopped in tests outside this change set: a GUI collapse-animation test while unrelated GUI files were being edited, and a Linux Flatpak proxy-override cleanup test that passed in isolation. Those results do not establish full-suite green under the concurrently changing workspace. All local proxy tests use synthetic upstreams; native Roblox consumption of the generated URL is unverified.

## Actual Sober client trial — 2026-11-03

**Live network-level acceptance confirmed on Sober 1.8.0 / Roblox Android, not a simulated upstream.** This was an isolated, temporary `FleasionProxy` listener on `127.0.0.1:44871`, with `FLEASION_ASSET_SYNTHETIC_CDN=1`, `FLEASION_ASSET_TRACE=1`, and a valid 4×4 PNG as the `Image` wildcard replacement. Sober was started with proxy variables scoped to that one Flatpak invocation. Its first six seconds were tunneled for bootstrap; subsequent assetdelivery and CDN connections used Fleasion's existing Sober TLS-splice path. No user's saved Fleasion replacement rules or permanent Flatpak proxy overrides were edited.

The client's authentic startup/home-screen traffic yielded **5 asset-delivery batch requests**, **190 active synthetic routes**, **222 CDN requests**, **190 completed local replacement responses**, and **three decrypted splice host connections**. Within the trace, new synthetic CDN GETs received valid `200` replacement responses, and the Roblox home screen loaded with account UI and game thumbnails. The client therefore really followed the generated CDN URL paths and received replacement bytes, validating the key URL-format and request-routing hypothesis for **this Sober build**. This is stronger than loopback replay, though the appearance of a particular substituted texture inside a running game was **not** independently confirmed. The PNG was deliberately a temporary diagnostic replacement, not an asset-specific rendered-image equivalence fixture.

The client emitted one `CONNECT tunnel failed, response 502` and associated AssetProvider warning early in startup; the isolated proxy summary recorded zero own splice/upstream errors. The evidence does not establish the failed request's precise cause or that every unrelated Roblox request succeeded. No same synthetic CDN URL was visibly refetched a second time in this session. In-game visual reload, later expiration, cache eviction, and QUIC/HTTP3 remain **untested**. Do not enable the feature by default for other clients on this basis alone.

Evidence retained on the user's Fedora host in `/tmp/fleasion-live-sober-synthetic-20261103/`: `metrics.json` (aggregate counters), `start.log` (startup/teardown), `sober.log` (native runtime startup), and `sober-live-small.jpg` (real loaded home screen). The experiment included an automatic deadline and **finished cleanly**, closing the temporary Sober client and its proxy; the original Fleasion GUI remained running and the pre-existing Sober Flatpak override remained unchanged.
